# What is Floating Garbage in Incremental Marking: Taking V8 as an Example

> **一句话摘要：** 当 GC 和程序执行交错进行时，有些对象在本轮标记过程中曾经可达、因而被标记；但到回收发生时，它们已经不可达。它们可能仍被本轮 GC 保留，这就是 **Floating Garbage（浮动垃圾）**。这是安全性与回收及时性之间有意识的权衡，而不一定是 GC 的 bug。

## 1. 从一个直觉上的“假阳性”开始

学习 V8 的 Incremental Marking（增量标记）时，我产生了一个疑问：

> 如果一个堆对象在增量标记的早期就被标记为灰色或黑色，但是 JavaScript 随后删除了所有通往它的强引用；等到最终完成 Major GC 时，这个对象实际上已经死亡了，GC 会不会错误地认为它仍然存活？

**会。** 更精确地说：在这次标记周期中，它**可能**已经获得了存活标记，即使在最终回收时不再从 GC Roots 可达，也不会因为引用删除就自动取消标记。

这类“被本轮 GC 保留、但现在已经不可达”的垃圾，通常称为 **Floating Garbage**。

这里的“假阳性”只是便于理解的类比：它是*对最终时刻可达性的过度近似*，并不意味着 V8 出现了内存安全错误。

## 2. 必要背景：三色标记与增量执行

把堆看成有向图：对象是顶点，强引用是边。GC 从 Roots（如栈、全局句柄等）出发，遍历仍然可达的对象。

经典三色抽象中，对象有三个状态：

| 颜色 | 含义 |
| --- | --- |
| 白色（White） | 尚未被本轮标记发现 |
| 灰色（Grey） | 已发现，但其引用字段还没有被完整扫描 |
| 黑色（Black） | 已完成扫描，当前已知的后继引用已被处理 |

简化的状态变化是：

```text
白色 --发现并加入工作队列--> 灰色 --扫描完成--> 黑色
```

对于正确完成的一轮追踪，仍然为白色的、属于本轮收集范围的对象可以回收；已经标记的对象则会保留。上述描述是算法抽象，具体的 V8 还存在弱引用、年轻代/老年代、只读空间、对象搬迁等特殊处理。

如果整个标记过程都是 Stop-The-World（STW），Mutator（执行 JavaScript、修改对象图的线程）不会在标记过程中改变对象之间的边。但**增量标记**把标记工作拆成多个时间片，时间片之间允许 JavaScript 继续执行：

```text
时间 ─────────────────────────────────────────────►
GC:       [标记一部分]       [标记一部分]       [最终标记/回收]
Mutator:                [继续执行并修改堆]  [继续执行]
```

V8 的增量标记**不是**“正式 Major GC 之前的独立预扫描”；它是**同一轮 Major GC 的标记工作的一部分**，之后还需要完成剩余标记及清扫/整理等步骤。[1][2]

## 3. Floating Garbage 是怎样产生的？

假设某时刻只有下面这条通往 B、C 的强引用路径：

```text
GC Roots
   |
   v
   A ------> B ------> C
```

考虑以下时序：

| 时刻 | GC / 程序行为 | B、C 的状态 |
| --- | --- | --- |
| t0 | 从 Roots 出发，A、B、C 都可达 | 尚未完全标记 |
| t1 | 增量标记发现并扫描 A、B、C | B、C 已被标记为黑色 |
| t2 | JavaScript 执行 `A.ref = null` | B、C 失去最后一条从 Roots 可达的路径 |
| t3 | 本轮标记完成，并执行回收 | B、C 仍持有本轮存活标记，可能保留 |

用两张图表示：

```text
在 t1：
Root --> A(黑) --> B(黑) --> C(黑)

在 t2：
Root --> A(黑)      B(黑) --> C(黑)
              X   （B、C 已不可达，但仍被标记）
```

B、C 在 **t1 曾经可达**，而在 **t2 已经不可达**；GC 对它们的“已发现”记录仍然有效。它们就成为这次收集周期中的 Floating Garbage。

注意：**不是“只要增量标记期间删除一条边，就必然产生 Floating Garbage”。** 如果 GC 在删除之后才检查原来的引用槽位，并且没有通过其他途径发现目标，那么这个目标有可能根本不会在本轮被标记。上述例子成立的关键是 **B、C 已在引用断开前被发现和标记**。

## 4. 为什么 GC 不把黑色对象重新改回白色？

直观想法是：既然 `A.ref = null` 了，为什么不把 B 的标记撤销？

问题是，**删除一条边与对象失去所有可达路径，不是同一回事**。

```text
Root --> A ----> C
     \-> B ----> C
```

即使删除 `A -> C`，C 仍然通过 `B -> C` 可达。为了判断 C 是否真的死亡，必须考虑其他指向它的路径；而一旦 C 失去可达性，它所指向的 D、E、F 是否也死亡，又是新的全局图问题。

因此，在常见的增量追踪设计中，本轮标记状态主要朝“未发现 → 已发现 → 已扫描”的方向推进，而不是随着每一次引用删除就对整棵对象子图做反向可达性证明。

这样做避免了大量重复遍历，让 GC 能分批推进，同时保障安全。代价则是：**标记记录会包含一些“曾经活着、现在已死”的对象。**

可以用集合形式描述这一现象。设：

- \(R(t)\)：时刻 \(t\) 从 Roots 经强引用可达的对象集合；
- \(M\)：本轮标记最终认定为存活的对象集合；
- \(t_f\)：本轮标记终止的时刻。

那么，简化模型下：

\[
\text{Floating Garbage} = M \setminus R(t_f)
\]

这个公式描述的是**标记集合相对于终止时刻可达集合的过近似**，不是 V8 用来计算 Floating Garbage 的实际实现公式。还应限定在本轮收集范围，并暂时忽略弱引用等特殊语义。

## 5. 为什么这种“假阳性”可以接受？

追踪式 GC 必须区分两种截然不同的错误：

| 情况 | 后果 | 是否可接受 |
| --- | --- | --- |
| **过度保留**：已不可达的对象仍被标记 | 占用更多内存，回收延迟 | 通常可接受 |
| **错误回收**：仍可达的对象没有被标记 | 可能产生悬垂引用、Use-After-Free 或崩溃 | 不可接受 |

GC 的重要正确性目标是：**不能错误地回收仍然可达的对象**。如果必须在“多留一点垃圾”和“可能回收活对象”之间选择，正确的 GC 会优先确保后者不发生。

而且，Floating Garbage 通常不会永久保留。如果 B、C 在下次覆盖它们所在空间的 Major GC 时依然不可达，新一轮标记就不会再从 Roots 发现它们，它们因而具备被回收的条件。

这不意味着“下一次任意 Minor GC 一定回收它们”：是否回收还与对象位于哪个代、该轮收集覆盖什么范围，以及其他运行时约束有关。

## 6. 它与 V8 的写屏障有什么关系？

现在考虑相反的危险：JavaScript **增加**了一条引用，导致一个白色对象从已扫描的黑色对象出发变得可达。

```text
修改前：Root --> A(黑)       C(白)
修改后：Root --> A(黑) ----> C(白)   （危险！）
```

如果 GC 已扫描完 A，未来不再访问 A，而 C 仍是白色，本轮可能错误地回收 C。为避免这种**漏标**，V8 在增量/并发标记时利用 **Marking Write Barrier（标记写屏障）**，让堆引用更新能够补充必要的标记工作。[1][3]

这就出现了一组很有意思的对照：

- **删除引用**之后，已经被标记的对象未必会取消标记 → 可能产生 Floating Garbage。
- **新增引用**之后，写屏障必须保证新可达对象不会被遗漏 → 即使这意味着有时多标记一些对象。

V8 在 2018 年介绍 Concurrent Marking 时，还明确提到：为了避免昂贵的内存屏障，它去掉了标记写屏障中对 **host 对象是否为黑色**的逐对象检查，因此写屏障会更保守，可能标记实际不可达的对象。[1]

这正是第二篇笔记《[Why V8 does not check the color of objects in Marking Barrier](./02-why-v8-does-not-check-host-color-in-marking-barrier.md)》要进一步展开的问题。

## 7. Floating Garbage 和 Memory Leak 有什么区别？

二者都表现为“内存暂时没有归还”，但机制完全不同：

- **Floating Garbage：** 对象已经不可达，只是本轮标记过度保留；未来合适的收集周期仍有机会回收。
- **Memory Leak（从 GC 可达性视角）：** 程序意外地一直保留有效强引用，例如某个长期存在的 Map、监听器或缓存持续持有对象，导致 GC 每次都会认为它可达。

因此，观察到一次 Major GC 后堆大小没有立即降到理论最小值，不足以断言程序发生了真正的内存泄漏；还需要结合跨多个收集周期的对象保留路径和内存趋势来判断。

## 8. 我的复习卡片

> **定义：** Floating Garbage 是标记过程中曾被视为存活、但在回收时已经不可达，因而被当前周期过度保留的对象。
>
> 
> **成因：** Mutator 在增量/并发标记期间修改对象图；本轮标记记录通常不会因删边就回退。
>
> 
> **代价：** 暂时额外占用内存；不等于永久内存泄漏。
>
> 
> **原则：** GC 可以保守地多保留对象，但不能漏标并错误回收仍然可达的对象。
>
> 
> **V8 语境：** 增量标记属于本轮 Major GC 的标记工作，之后的最终标记不会默认从零重新计算所有当前可达对象。
